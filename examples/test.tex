\chapter{ Inicio }

\section{ Primeras ideas }

Este proyecto tiene disintas finalidades, el conocer como se crea un lenguaje, como es que se
define y se consume una sintaxis. Ahora, eso tambien permite crear nuevas preguntas derivadas,
por ejemplo ¿por que hay diferencia de velocidad de ejecución?

Ya se que la respuesta es porque es compilado, interpretado o medio medio como Java, pero la
pregunta en realidad es, ¿por que obtaron por ese resultado y como eso cambia la forma en que
el compilador fucniona?

Inicialmente se me ocurrio parsear por \note[exresiones regulares]{Es definir patrones que se
pueden indetificar y capturar}, es decir, buscaba por patrones,
ej, \backslash command\{.*\}\{ .*(Contenido) \} y al incio puede parecer util, pero el problema
ahora sera anidar porque \backslash command\{.*\}\{ \backslash command\{...\} \} genera
problema con el cierre pues el cierre \} del comando interior cierra al superio y deja fuera
un \} que seria su cierre real. Entonces puedes sumar la posicion y agregar \} pero entonces
lo mismo pasaria al anidar otro y llevar un contador, una \textbf{profundida}.

Ya que la expresion se empieza a volver compleja, unicamente para comandos, en entornos se
pone un poco peor porque ya no solo se controlad desde el regex, sino que se deben crear
funciones para extraer el contenido hasta el cierre. Asi que si un regex no es el ideal,
la alternativa seria trabajar caracter a caracter o un regex diferente.

\section {El núcleo  }

Decidí cambiar el mecanismo para crear el arbol. Anteriormente probe con \textbf{expreciones regulares}

\section{           La alternativa}

La siguiente idea es, acumular los caracteres hasta encontrar un caracter de ejecución, un
caracter especial. La idea es, para leer un comando \backslash command\{....

Entonces se lee \backslash, significa que empieza un comando, lo siguiente será el nombre
que define que comando es, asi que empieza a leer las letras, y vamos almacenando ese valor:

\begin{enumerate}
  \item c
  \item o
  \item ....
  \item \{
\end{enumerate}

Y de momento, pum, encontramos el caracter \{, eso implica una acción, es decir, el comando
que se leyo fue \textit{command}, este comando comienza a leer el contenido del grupo que
tiene \{...\}. Suena bien pero, y si estas en modo matematico, el contexto dice que \{ no es
un comando de acción, es un literal, entonces no lo proceses, por otra parte, si estas en
un contexto normal y encuentra un \{ entonces querra evalularlo y falla por no tener comando
acumulado asi que el contexto indicará que hacerle, lo mismo para [, etc... Esto complica
la lectura, seran muchas validaciones y aun que tengo un control completo porque incluso
podria definir nuevos contexto, agregar comandos y leer sus parametros se complica.

Esto es parecido a como sumar 2+2 y hacerlo mediante union de conjuntos, mucho control,
mucha complejidad. Aun creo que usar regex parece ser mejor opcion pero debe ser simple...

\chapter{ Tokens como en la IA }

navegador permite indicar como renderizarlo, asi que el arbol que genera el parser no se

El primer paso es crear el tokenizador. Los primero comandos integrados fueron una prueba,
se agregaron comandos como \backslash section, \backslash\backslash y estilos de texto. Esto

\section{ Entornos }

Con esa base mas limpia, los entornos fueron lo primero en implementarse. \texttt{enumerate}
e \texttt{itemize} fueron el primer soporte, En retrospectiva no fue la mejor idea porque estos
entornos definen los elementos de su interior mediante \backslash item, entonces no tienes un
cierre como tal, es un \textit{cierre implicito}. Eso complica todo porque:

\begin{enumerate}
    \item Detectar los items es buscar un comando particular
    \item La anidación nativa
    \item \begin{enumerate}
            \item Si un entorno no cierra
            \item Los demas fallaran
          \end{enumerate}
\end{enumerate}

Pero si se integra bien, entonces en lugar de buscar directamente \backslash item, puedo usarlo
para buscar otros elementos.

\begin{itemize}
    \item Test de lista
    \item Prueba con inline math $\int 2x^{3y}$
    \item Cierre implicito del anterior
\end{itemize}

Y permiten leer ecuaciones inline, asi que creo que al menos lo básico de una lista, funciona.

\chapter{ Custom components }

\section{ Bloques }

Para poder registrar nuevos elementos se expandio el sistema de registros. En ese commit se agrego
soporte a \backslash backslash, saltos de linea con doble backslash, el entorno \texttt{block}
y caracteres especiales. Con esos nuevos registros disponibles, los bloques pudieron implementarse.

La idea es mostrar distintas versiones de un contenido alternando entre ellas con botones.
El primer intento fue un comando \backslash block\{c1\}\{c2\}\{...\} pero la cantidad de
subbloques es variable, lo que complicaba el registro y la deteccion del cierre. Usar items
resulto ser la solucion mas pragmatica.

Creamos ahora un bloque, que permite agrupar elementos y mostrarlos mediante botones:
\begin{block}
   \item Son utiles para mostrar distintas demostraciones del mismo elemento.
        Por ejemplo, en Topologia se puede abordar desde 2 perspectirvas, por un lado
        usar metricas y por otro lado, el concepto de bolas.
        Creo que puede ser util no tratarlos de forma indistinta puesto que, aun que
        las \note[bolas]{Una bola es un subconjunto de $R^n$} aparecen como una
        consecuencia de tener una metrica, las bolas
        por si mismas tambien son un concepto que no necesariamente requeiren de
        tener definida una metrica.
    \item Uno de los problemas al crear este entorno es la clara separacion de los
        distintos bloques.
        
        En primera instancia, se intento con un comando tipo \backslash block\{c1\}\{c2\}\{...
        Pero esto es un problema porque la cantidad de argumentos o "subbloques"
        es variable y eso hace que crear un registro se vuelva mas complejo y determinar
        el cierre tambien.
    \item Si bien, no me agrada del todo usar items, es verdad que es mucho mas simple
        usar items e identaciones para organizar el codigo
\end{block}

Y los bloques a su vez, puede contener cualquier elemento que se requiera, tanto ecuaciones
como imagenes, notas, etc.

Y ahora integramos referencias. Esto se logro con un diccionario label:\{id, index\}, asi cuando
se crea una nueva referencia, entonces tenemos la key y automaticamente, un contador. Los
contadores formales aun no se agregan.

\chapter{ Referencias }

Se agrego la lista de referencias. Cada \backslash label genera una entrada en un diccionario
\texttt{label:\{id, index\}} con un contador automatico. Esto tambien implico un cambio en el
output: ya no es un array sino un diccionario, pues las referencias viven como hermanos del
arbol y no dentro del flujo del texto. Junto con esto, el parser se refactorizo en archivos
de una sola responsabilidad.

\begin{equation}
    E = mc^2
\end{equation}
\label{eq:einstein}

Y se citan con \backslash ref\{id\}, ej, \ref{eq:einstein}

Como se agregan al output como hermano del arbol, este ya no regresa un array sino un diccionario.

Por fin se agregaron los custom components de la libreria original. Sin embargo, crear una
retrocompatibilidad implico un cambio grande en dichas librerias.

\chapter{ Customs components }

Los custom components de la libreria original existian antes del parser, pero integrarlos
requirio retrocompatibilidad, lo que implico cambios importantes. La decision fue dejar de
tratarlos como comandos inline y convertirlos en entornos con key-value props. Asi, siguen
la misma sintaxis que el parser ya conoce y el escritor no necesita aprender nada nuevo.

En este punto, el core ya parsea la base de latex, se pueden integrar equaciones, listas, imagenes, referencias
y algun elemento mas. Si bien, con esto ya se pueden crear documentos, tambien es cierto que una intencion de este
"parser" es expandir LaTeX de una forma sencilla. Sin tener que aprender otra sintaxis y semantica, unicamente se
agregan algunos comandos o componentes extras. Estos siguen la sintaxis de latex y como ya podemos leer y
procesar la sintaxis de latex, la adaptacion del escritor a nuevos componentes es relativamente sencilla.

\section{ Capitulos }

Se creo soporte para capitulos y secciones. Sin esto, todo el contenido vive en un solo
nivel y no es posible crear una tabla de contenido ni anclas de navegacion. Es algo
fundamental para documentos largos como libros o apuntes.

En este punto, se integran las secciones y capitulos. Algo esencial al momento de escribir
documentos largos (libros, notas). Esto permite separar el contenido en agrupaciones con
informacion relacionada. A su vez, nos permite crear una lista de capitulos para crear
referencias y permitir al usuario viajar rapido entre contenido.
